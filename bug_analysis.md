# 🐛 Анализ ключевых баг-репортов (API проекта «Помоги лично»)

Этот документ содержит детальный разбор наиболее показательных дефектов, выявленных в ходе тестирования API. Эти кейсы демонстрируют работу с «серыми зонами», противоречиями в требованиях и проблемами интеграции.

## 1. Кейс: Противоречие в логике обработки ошибок (Блок `/share/`)
**ID бага:** BR_APIdoc_shr_1
**Приоритет:** Высокий
**Эндпоинт:** `PATCH /share/`
**Метод:** PATCH

### Суть проблемы
В требованиях (ТЗ) и документации Swagger были указаны **взаимоисключающие** ожидаемые результаты для сценария передачи некорректного значения параметра `icon`:
*   Вариант А: `400 Bad Request` (ошибка валидации).
*   Вариант Б: `404 Not Found` (объект не найден).

### Фактическое поведение системы
При воспроизведении сценария с некорректным значением (`"icon": "error"`) сервер стабильно возвращал код **400 Bad Request** с детализацией ошибки:
```json
{
  "error": "Валидация завершилась с ошибкой",
  "details": {
    "icon": ["Выбрана неправильная иконка."]
  }
}
```

## 2. Кейс: Расхождение ключей в JSON-ответе (Блок `/whom_we_helped/`)
**ID бага:** BR_APIdoc_whmhlp_2  
**Приоритет:** Высокий  
**Эндпоинт:** `GET /whom_we_helped/`

### Суть проблемы
Несоответствие наименований параметров в документации Swagger и реальном ответе сервера:
*   В Swagger указано: `results` и `count`.
*   Фактический ответ сервера: `result` и `total_objects`.

### Почему это критично
Это классическая проблема интеграции. Если фронтенд ожидает массив под ключом `results`, он получит `undefined`, так как в ответе лежит `result`. Данные не отобразятся на экране, хотя сервер их успешно вернул. Пользователь увидит пустой список, думая, что информации нет, хотя она есть — просто ключи не совпали.

### Моё решение
*   Выявил проблему через сравнение Swagger-спецификации и реального ответа в Postman.
*   Рекомендовал привести документацию к виду реального ответа (или наоборот, если логика сервера должна быть изменена) для устранения риска падения фронтенда.


## 3. Кейс: Отсутствие обязательного идентификатора в ответе (Блок `/contacts/` и `/org_reports_yearly/`)
**ID бага:** BR_API_con_1 / BR_API_orgrepyr_1
**Приоритет:** Высокий
**Эндпоинт:** `GET /contacts/`, `GET /org_reports_yearly/`

### Суть проблемы
При запросе данных сервер возвращал успешный ответ (200 OK), но в теле ответа **отсутствовал критически важный параметр `id`**.

**Пример фактического ответа (без `id`):**
```json
{
  "contact_type": "phone",
  "title": "Основной номер",
  "details": "+7 (999) 000-00-00"
  // Параметр "id" отсутствует
}
```

## 4. Кейс: Нарушение бизнес-логики и пагинации (Блок `/they_need_help_too/`)
**ID бага:** BR_API_theynhlp_2  
**Приоритет:** Критический  
**Эндпоинт:** `GET /they_need_help_too/`  
**Метод:** GET

### Суть проблемы
Согласно требованиям, эндпоинт должен возвращать список из **10 семей**, которым нужна помощь, отсортированный по статусу сборов. Однако фактический ответ сервера содержит всего **2 записи**. Кроме того, в ответе отсутствует параметр, позволяющий оценить корректность сортировки.

### Фактическое поведение системы
При запросе `GET /they_need_help_too/` сервер возвращает статус **200 OK**, но данные не соответствуют ожиданиям.

**Ожидаемый результат:**
```json
[
  { "id": 1, "family_name": "Семья 1", "image": "..." },
  { "id": 2, "family_name": "Семья 2", "image": "..." },
  // ... и так далее
  // Всего 10 элементов, отсортированных по статусу сборов
]
```

## 5. Кейс: Нарушение структуры данных в ответе (Блок `/settings/frontend/`)
**ID бага:** BR_API_set_1
**Приоритет:** Критический
**Эндпоинт:** `GET /settings/frontend/`
**Метод:** GET

### Суть проблемы
Согласно ожиданиям (документации/ТЗ), эндпоинт должен возвращать **список** настроек для фронтенда (массив объектов), чтобы интерфейс мог динамически отобразить все доступные параметры. Однако сервер возвращает всего один объект с двумя полями, что ломает логику рендеринга на клиенте.

### Фактическое поведение системы
При запросе `GET /settings/frontend/` сервер отвечает статусом **200 OK**, но структура JSON не соответствует ожиданиям:

**Ожидаемая структура (список):**
```json
[
  { "key": "theme", "value": "dark" },
  { "key": "language", "value": "ru" },
  { "key": "currency", "value": "RUB" }
  // ... и другие настройки
]
```
