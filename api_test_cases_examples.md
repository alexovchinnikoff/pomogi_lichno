# Примеры тест-кейсов: Граничные значения пагинации

## Кейс: Проверка обработки `limit=0` в галерее изображений
**ID:** `API_supgal_31`  
**Модуль:** `support_us_gallery`  
**Приоритет:** Высокий  
**Тип:** Граничное значение (Boundary Value Analysis)

| Параметр | Значение / Описание |
| :--- | :--- |
| **Эндпоинт** | `GET /support_us_gallery/{id}/images/` |
| **Метод** | `GET` |
| **Входные данные** | `limit=0` (параметр пагинации) |
| **Предусловия** | 1. Стенд доступен (`pl.rassokha.pro:8001/api/v1`).<br>2. В галерее существуют изображения. |
| **Шаги воспроизведения** | 1. Отправить GET-запрос на эндпоинт `/support_us_gallery/1/images/`.<br>2. Добавить query-параметр `?limit=0`. |
| **Ожидаемый результат (OR)** | **Статус:** `200 OK`<br>**Тело ответа:**<br>```json<br>{<br>  "count": 0,<br>  "next": null,<br>  "previous": null,<br>  "results": []<br>}<br>```<br><br>*Логика:* Сервер должен явно вернуть пустой массив `results`, подтверждая отсутствие запрошенных элементов. |
| **Фактический результат (AR)** | **Статус:** `200 OK`<br>**Тело ответа:** Возвращается стандартный набор данных (например, 6 элементов) **ИЛИ** ошибка валидации.<br><br>*Проблема:* Сервер игнорирует значение `0` и применяет дефолтное значение лимита, либо обрабатывает запрос некорректно. |
| **Статус проверки** | Failed (неуспешно) |
| **Выявленный риск** | **UI/UX баг:** Фронтенд-приложение ожидает пустой массив для отображения состояния «Нет изображений». Из-за получения реальных данных логика отображения ломается, пользователь видит контент вместо понятного сообщения об отсутствии данных. |
| **Мой вклад** | 1. **Выявил сценарий:** Заметил отсутствие проверки граничных значений для параметра `limit`.<br>2. **Воспроизвел баг:** С помощью Postman подтвердил нестабильное поведение при `limit=0` и `limit=-1`.<br>3. **Сформулировал требование:** Предложил явно обрабатывать случаи `limit <= 0`, возвращая пустой список.<br>4. **Задокументировал:** Зафиксировал кейс и передал в баг-трекер (ссылка на баг-репорт). |
| **Артефакты** | • Баг-репорт в трекере.<br>• Запись в файле `bug_analysis.md` (раздел «Пагинация и лимиты»). |
| **Рекомендации** | Добавить серверную валидацию: если `limit <= 0`, принудительно возвращать `results: []` без выборки из БД. |


## Кейс: Нестабильность обработки ошибок при передаче некорректного значения page ID: API_blg_5
Модуль: blog
Приоритет: Высокий
Тип: Негативное тестирование / Анализ консистентности ошибок
Параметр	Значение / Описание
Эндпоинт	GET /blog/?page={page}/
Метод	GET
Входные данные	Параметр page со значением -1 (отрицательное число).
Предусловия	1. Стенд доступен (pl.rassokha.pro:8001/api/v1).
2. В системе есть опубликованные блоги.
Шаги воспроизведения	1. Отправить GET-запрос на эндпоинт /blog/.
2. В query-параметре указать page=-1.
Ожидаемый результат (OR)	Статус: 400 Bad Request
Тело ответа: Сообщение об ошибке валидации (например: «page must be a positive integer»).

Логика: Так как -1 — это некорректное значение для номера страницы, сервер должен вернуть ошибку валидации входных данных (400).
Фактический результат (AR)	Статус: 404 Not Found (в некоторых случаях 400 Bad Request).

Проблема: Поведение сервера нестабильно. Он путает два разных типа ошибок:
1. 404 Not Found: Ресурс не найден (нет страницы с таким ID).
2. 400 Bad Request: Клиент прислал неверные данные (отрицательное число).
Это ломает логику обработки ошибок на фронтенде: фронтенд не может понять, проблема в данных пользователя или в отсутствии контента.
Статус проверки	Skipped / Known Bug (требует уточнения требований)
Выявленный риск	Сложность отладки: Разработчики фронтенда не могут корректно обработать ошибку, так как код ответа меняется непредсказуемо.
Плохой UX: Пользователь может получить сообщение «Страница не найдена», хотя он просто ввел отрицательное число, которое нужно было отклонить как ошибку ввода.
Мой вклад	1. Выявил несогласованность: Заметил, что разные типы некорректных данных приводят к разным кодам ответа без четкой логики.
2. Проанализировал последствия: Объяснил команде, почему смешение 400 и 404 опасно для интеграции.
3. Предложил решение: Рекомендовать унифицировать обработку ошибок для query-параметров:
- Все ошибки валидации параметров (page, limit, offset) должны возвращать 400 Bad Request.
- 404 Not Found должен использоваться только если запрошенный ресурс (например, конкретный блог по ID) действительно отсутствует.
4. Задокументировал: Зафиксировал кейс в bug_analysis.md с пометкой «Требуется уточнение требований к обработке ошибок».
Артефакты	• Баг-репорт с примерами разных ответов сервера.
• Запись в bug_analysis.md (раздел «Обработка ошибок и коды состояния»).
• Предложение по обновлению Swagger-документации.
Рекомендации	1. Унифицировать коды ответов для ошибок валидации query-параметров (всегда 400).
2. Добавить в документацию четкие правила: какие коды ошибок ожидаются для каких типов сбоев.
3. Реализовать middleware-обработчик ошибок, который нормализует ответы API.
